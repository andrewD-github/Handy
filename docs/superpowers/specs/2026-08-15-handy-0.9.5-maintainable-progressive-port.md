# Handy 0.9.5 Maintainable Progressive Port

**Date:** 2026-08-15

**Status:** Approved

## Objective

Upgrade the custom Handy build from 0.8.3 to the stable 0.9.5 architecture while preserving the user's defining workflow: transcription text progressively appears directly in the application prompt where dictation began. Structure the customization as a small extension of upstream Handy so later upgrades can be rebased and tested without merging two transcription architectures.

## Baseline

- Base: official Handy `v0.9.5`.
- Selected post-release fix: `9e534a3`, keeping Hugging Face model data under the portable `Data` directory.
- The current installed executable remains unchanged until the candidate passes every release gate.
- The rejected clipboard-based target-content guard is preserved in a named stash and is not part of this port.
- The upstream Rust baseline passes 174 tests on Windows.
- Exact frontend dependencies were installed without weakening TLS. ESLint, translation consistency, typecheck, and the production Vite build pass.

## Architecture

### Upstream remains authoritative

Official Handy owns audio capture, model loading, streaming inference, stream finalization, history, paste transactions, overlay behavior, and platform support. The custom build will not restore the old repeated full-window batch scheduler.

### One isolated direct-prompt module

Create a `progressive_dictation` module with three responsibilities:

1. Track one direct-prompt session using an opaque generation identifier and captured Windows target identity.
2. Convert upstream `StreamTextEvent` snapshots into append-only prompt edits. The displayed stream (`committed + tentative`) is typed only while it grows from the exact text already inserted; a retraction is never enacted with backspaces.
3. Reconcile the finalized transcript against text already committed by the module, with explicit outcomes and diagnostics.

The module exposes a small public API (`start`, `apply_snapshot`, `finish`, and `cancel`). The transcription manager publishes stream snapshots through this API but contains no prompt-editing policy. The action layer owns lifecycle calls but contains no diff or stability logic.

### Output modes

Add a setting with two values:

- `overlay`: official Handy behavior.
- `direct_prompt`: append-only streaming display text is inserted at the dictation target as it becomes available.

The custom build migrates the user's existing progressive setting to `direct_prompt`. New/default upstream installations retain `overlay`, keeping the patch suitable for rebasing and potential upstream discussion.

### Prompt editing policy

- Append the newly visible suffix while the full streaming display extends the text already typed.
- Never enact a model retraction and never backspace during live dictation.
- Reject duplicate, stale, shrinking, or contradictory display snapshots and record why.
- Every edit is tied to the active session generation.
- Before every edit, verify that the original target is still eligible. On Windows this includes foreground-window, focused-control identity, and a physical pointer-click interaction epoch. Mouse movement does not affect the epoch; a click fails closed so submitting/clearing a Chromium prompt cannot receive a late tail.
- Finalization may append a suffix when the final transcript extends the typed display text.
- A material final disagreement is not silently rewritten. It is recorded for diagnostics and handled by the separately tested final-reconciliation policy; the unsafe clipboard guard is not revived.
- Starting or cancelling a new session invalidates every edit from the previous generation.

### Upstream paste integration

Use Handy 0.9.5's paste transaction and rich clipboard restoration mechanisms instead of the old text-only clipboard implementation. The direct-prompt adapter will call a narrow editing interface so Windows injection details stay outside transcription policy.

### Diagnostics

Each session records:

- session generation and target identity;
- stream snapshot timing, committed/tentative lengths, and acceptance outcome;
- inserted character counts and edit latency;
- finalization timing and reconciliation outcome;
- target-guard, stale-generation, and cancellation decisions;
- selected model, accelerator, output mode, and relevant settings.

Diagnostics must not contain secrets or clipboard contents unrelated to the active transcript.

## Repository Maintenance Model

- `upstream/main`: fetched official Handy history; never customized.
- `codex/handy-0.9.5-progressive`: small custom patch stack based on a stable upstream tag.
- Candidate executables are built and tested separately from `D:\Apps\Handy`.
- Custom commits are ordered by concern: architecture, prompt adapter, settings/UI, diagnostics, then packaging/docs.
- A patch inventory documents every upstream touchpoint and why it exists.

## Data Preservation

The integration must preserve `D:\Apps\Handy\Data`, including settings, history, recordings, diagnostics, logs, and downloaded models. Installation replaces only the executable and required runtime assets after a timestamped backup.

## Verification and Release Gates

The candidate is not installable until all of the following pass:

1. Rust unit tests, formatting, and relevant lint checks.
2. Frontend typecheck/build, ESLint, formatting, and translation consistency without disabling certificate verification.
3. Existing Handy batch transcription and overlay behavior remain functional when output mode is `overlay`.
4. Direct-prompt live text is append-only and appears in the original prompt.
5. Stale updates cannot appear after stop, cancel, focus change, submit, or a subsequent F4 session.
6. Clipboard text, images, and rich formats are restored by upstream's paste transaction behavior.
7. The same real saved WAV sessions are replayed through the candidate and compared with the recorded 0.8.3 baseline. Claims are limited to determinism, latency, churn, and rewrite measurements unless trustworthy corrected references exist.
8. Representative live tests cover ChatGPT submission followed by a new F4 session, Word/Notes-style editors, cancellation, focus switching, and rapid session restart.
9. The installed executable is backed up and replaced only after the user-facing acceptance checklist passes.

## Explicit Non-goals

- No claim of true WER or CER without trustworthy reference transcripts.
- No restoration of the old repeated batch inference scheduler.
- No backspacing or replacement of volatile live hypotheses in the prompt.
- No installation of the rejected target-content guard.
- No automatic replacement of the current daily-driver executable before validation.
