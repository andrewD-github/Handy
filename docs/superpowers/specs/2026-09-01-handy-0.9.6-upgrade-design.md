# Handy 0.9.6 Custom Upgrade Design

**Date:** 2026-09-01

**Status:** Approved

## Objective

Upgrade the user's verified custom Handy installation from official Handy v0.9.5 plus the focused-field direct-prompt extension to official Handy v0.9.6, without losing the direct-in-prompt streaming experience, append-only safety policy, Submit/F4 residual-text protection, diagnostics, settings, portable data, installer, or rollback path.

Codex owns the integration, testing, installation, launch, and post-install verification. The user's current working installation remains available unless and until the candidate passes the release gate.

## Selected Integration Approach

Merge the official `v0.9.6` tag into the existing customization branch and reconcile the small custom extension against the new upstream implementation. This preserves upstream history and makes later official upgrades easier to review than copying release files or rebuilding the customization from scratch.

The alternatives were rejected:

- Replacing the installed executable with the official release would remove direct-prompt output and its safety behavior.
- Copying selected upstream files would obscure provenance and risk omitting interdependent changes, particularly the transcribe.cpp 0.2.0 update.

## Upstream Scope

The v0.9.6 integration includes all official changes, including:

- transcribe.cpp 0.2.0 and associated transcription/audio updates;
- portable Hugging Face model storage fixes;
- default-microphone fallback after device disconnect;
- multi-word custom-word support and filler-word changes;
- tray-icon single-writer/race fixes;
- overlay/theme propagation fixes;
- dependency, binding, catalog, translation, and build updates.

No upstream feature will be selectively dropped merely because it touches a customized file.

## Customization Boundary to Preserve

- `progressive_dictation.rs` remains the owner of direct-prompt session and append-only display policy.
- Upstream transcription code supplies streaming snapshots; it does not own prompt-editing policy.
- The action layer owns session lifecycle calls without duplicating progressive text logic.
- Windows input/clipboard helpers preserve the guarded target identity, physical-click epoch, atomic append barrier, and rollback-safe failure behavior.
- Mouse movement alone never invalidates a session; a physical click, target/focus change, cancellation, stop completion, or new generation does.
- The Advanced setting and generated bindings preserve `overlay` and `direct_prompt` output modes.
- Diagnostics, replay tooling, transactional installer, release checklist, and the custom blue theme token remain available.

## Conflict and Semantic Review

The mechanical merge preview identifies direct conflicts in:

- `src-tauri/src/input.rs`
- `src-tauri/src/settings.rs`
- `src/App.css`
- `src/components/settings/advanced/AdvancedSettings.tsx`

Those conflicts will be resolved by retaining both the upstream v0.9.6 behavior and the customization boundary above. Files that merge automatically but sit on the runtime boundary—including actions, transcription manager, clipboard, library initialization, settings bindings, portable mode, shortcuts, overlay, and Cargo dependencies—will receive an explicit semantic review. A clean merge alone is not acceptance evidence.

## Data and Installation Safety

- Do not alter `D:\Apps\Handy\Data` during candidate development or replay testing.
- Build the candidate in the existing isolated Git worktree, not in the installed application directory.
- Preserve settings, history, recordings, diagnostics, logs, and downloaded models.
- Create a timestamped backup of the working installation before replacement.
- Verify the candidate executable hash and package contents before installation.
- If installation or launch verification fails, restore the backup and relaunch the known-good version.

## Automated Release Gate

The candidate must pass all applicable repository checks, including Rust tests and formatting, frontend type checking/build/lint/formatting, translation consistency, installer tests, and progressive-dictation unit/integration tests.

It must also replay the same 17 saved real-world recording sessions used for the v0.9.5 release gate. The comparison will measure observed output, first-visible latency, stop-to-final latency, append-only behavior, stale-event rejection, final reconciliation, and failures. It will not claim WER or CER without trustworthy reference transcripts.

Acceptance requires:

- all 17 replay sessions complete without a safety failure;
- zero visible live backspaces or retractions;
- no stale tail can be inserted after a physical click/Submit, cancellation, focus change, completed stop, or a newer F4 generation;
- direct-prompt streaming remains progressive and append-only;
- overlay mode remains usable;
- no material regression from the verified v0.9.5 latency baseline (p95 first visible 2.25 seconds; p95 stop-to-final 0.51 seconds), with any unavoidable measurement variance reported rather than hidden;
- portable data and settings migration tests pass.

## Rollout and Observation

After the gate passes, stop Handy, create the backup, install the verified v0.9.6 candidate transactionally, and launch it. Confirm that it reports v0.9.6, loads the existing model and settings, retains `direct_prompt`, can start and stop a transcription session, and writes no startup/runtime error indicating a broken migration.

Automated replay proves the deterministic safety and performance gates. It cannot fully prove interaction with every live third-party editor. The handoff will distinguish automated and locally observed checks from any live application interaction that cannot be exercised without speaking into the user's microphone.

## Failure Policy

If any required test or replay check fails, do not replace the current installation. Diagnose and repair the candidate, rerun the affected checks and then the full release gate. If post-install launch verification fails, roll back automatically to the timestamped backup.
